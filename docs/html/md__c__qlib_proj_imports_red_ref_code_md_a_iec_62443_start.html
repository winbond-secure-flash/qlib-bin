IEC 62443 Code Reference for W77Q Secure Flash

The IEC 62443 series of standards define requirements and processes for implementing and maintaining electronically secure Industrial Automation and Control Systems (IACS). These standards set best practices for security and provide a way to assess the level of security performance. Their approach to the cybersecurity challenge is a holistic one, bridging the gap between operations and information technology as well as between process safety and cybersecurity.

This reference maps IEC 62443 requirements to W77Q features and example C code. For more information about IEC 62443 compliance, see application note AN0200036. Each requirement links to further explanation and relevant code examples.

Secure Data Storage / Cryptographic Write Protection

W77Q provides a fundamental contribution to device security through its secure-storage feature. Cryptographically protected policies can be applied to flash sections. Once the policies and keys are configured, flash access is governed by the selected security rules. Section policies provide multiple attributes that can be used to implement a security architecture.

# plain read/write policy attribute has no keys has restricted key has full access key
1 plain read enabled, plain write enabled read write read write read write
2 plain read enabled, plain write disabled read write read write read write
3 plain read disabled, plain write disabled read write read write read write

Secure Log

W77Q provides a fundamental contribution to device logging through its secure-log feature.

Logs can use different access policies, including plain, read-only, and full access. This stack-like feature can support logging use cases such as:

  • device event log
  • additional rollback protection by securely storing information about previous update events, including updates unrelated to firmware.

To use a section as a log, configure it with the log attribute. Log entries can be appended to the log and read, but cannot be erased individually; erasure applies to the entire section. Access restrictions are similar to those for secure storage and depend on the section's PA_R (plain read) and PA_W (plain write) policy settings.

# PA_R / PA_W section policy has no keys has restricted key has full access key
1 PA_R enabled, PA_W enabled read append erase read write erase read append erase
2 PA_R enabled, PA_W disabled read append erase read append erase read append erase
3 PA_R disabled, PA_W enabled read append erase read append erase read append erase
4 PA_R disabled, PA_W disabled read append erase read append erase read append erase

Example implementation

The secure-log example has two phases: manufacturing and field use. During manufacturing, three secure-log sections are configured with different policies. During field use, the example demonstrates how each policy affects log operations.

Secure Firmware Updates using Symmetric / Asymmetric Cryptography

W77Q provides atomic firmware updates, a fundamental security feature.

Firmware updates use a rollback section divided into active and inactive halves. The new firmware is written to the inactive half. Once writing is complete, a cryptographically protected swap command atomically exchanges the two halves. This allows the new firmware to be written gradually, including while the device is in a low-power state, while the final swap completes as a single operation. The swap command can use symmetric or asymmetric cryptographic protection.

Symmetric cryptography based

With symmetric cryptography, the section configuration command is issued during a secure session with the device. It is sent from the local or remote host to the connected W77Q device as an encrypted SPI transaction.

Asymmetric cryptography based

With asymmetric cryptography, a secure session with W77Q is not required. The host creates a section configuration string, potentially offline, and signs it with the private key of an LMS key pair. The host sends the string and signature to W77Q. The device verifies the string using the corresponding LMS public key and, if verification succeeds, executes the configuration command.

Benefits/Drawbacks

Symmetric cryptography requires a secure session with the device, so each update flow is specific to that device. However, symmetric keys are straightforward to generate using the HKDF function.

Asymmetric cryptography does not require a secure session with the device. It supports a broadcast update by signing the section configuration string with a private key. However, generating an asymmetric key pair is more complex.

Example implementation

The firmware-update example has manufacturing and field-use phases for both symmetric and asymmetric methods. During manufacturing, flash is configured with the required layout and policy: shared keys are configured for the symmetric method, while only the public LMS key is configured for the asymmetric method. The example configures a rollback section and demonstrates both update methods.

Platform Firmware Resiliency

W77Q provides fundamental support for device resilience.

Read-only boot memory (cryptographically write-protected boot section)

The boot section can be configured so that only authorized users can write to it; other actors can read it only. See the secure-storage example for configuration details.

Integrity-protected fallback (remapping the boot section after an integrity failure)

If the boot section fails its integrity check, W77Q automatically redirects boot-section (section 0) access to the configured fallback section. The device can then boot from the fallback firmware, which may handle the incident and help maintain availability.

Example implementation

The resiliency example has manufacturing and field-use phases. During manufacturing, three sections are configured for the fallback demonstration. During field use, the boot-section integrity is deliberately invalidated to demonstrate redirection of reads to the fallback section.

Section 0 — [0–1 MB]

This is the boot section to protect with an integrity policy. Plain read access is enabled, and plain write access is disabled. This example uses CRC-32; digest-based integrity (SHA-256) is also supported.

Section 1 — [0–2 MB]

This section overlaps section 0 and is used to demonstrate how its integrity can be invalidated. Plain read and write access are enabled.

Section 7 — [2–3 MB]

This is the fallback section to which section 0 access is mapped if section 0 fails its integrity check. It can hold recovery firmware. Plain read and write access are enabled.

Integrity monitoring (periodic digest calculation for section data)

Another way to maintain device availability is to monitor integrity. W77Q can calculate a digest of a flash section to detect data corruption. The request can be signed, giving the local or remote host both the digest to compare with an expected value and assurance that the response came from W77Q rather than being spoofed in a man-in-the-middle attack. A successfully verified signed command can also support device attestation.

Secure Erase

W77Q provides secure erase, which can make data in NOR flash unrecoverable.

Data stored on W77Q can be erased. If a flash section is write-protected by a key, the secure erase command must be authenticated with that key. Formatting also deletes the device contents, including previously configured keys. A secure format command is authenticated with the device master key.

The deletion rules are simple:

  • If a section is write-protected, the corresponding full-access key is required to erase data within it.
  • A read-access key does not authorize erasing the section.
  • If plain format is disabled, the device master key is required to format the device; otherwise, a plain format command can be used.

Example implementation

The erase example has manufacturing and field-use phases. During manufacturing, flash sections are configured with different policies. During field use, the example demonstrates which erase operations are available under each policy.

Winbond Identifier, Secure Unique ID

Each W77Q device has unique identifiers programmed during manufacturing. These identifiers can be read without a secure session:

  • UID — Standard flash unique ID. Programmed by Winbond during manufacturing; read-only and retained through device formatting.
  • WID — Secure flash unique ID. Programmed by Winbond during manufacturing; read-only and retained through device formatting.
  • SUID — Secure user ID. Set by the user; readable and writable, and erased when the device is formatted.

Remote Attestation

Direct Attestation

The W77QxxN supports direct establishment of a root of trust without requiring the local MCU to participate in the cryptographic operation. The device can verify a section's digest, make the section cryptographically write-protected, and securely report its status to a remote user over a secure channel.

A remote authorized user first establishes a secure channel directly with the W77QxxN. The user then reads and authenticates the digest of firmware stored in secure flash. The secure channel is based on a master key that establishes the device's hardware identity; the firmware digest establishes its software identity. Together, these checks authenticate both identities and provide the basis for a root of trust.

🔗Direct attestation sample

DICE-Like Device Attestation

The W77QxxN provides hardware functions that support DICE-like attestation and generation of the Compound Device ID (CDI). The CDI is derived from the Unique Device Secret, which identifies the hardware, and the firmware digest, which identifies the software. The device hashes the boot code in section 0 to compute the CDI. A user can then establish a session and securely read the CDI from section 0. This operation is allowed only if section 0 is the only section accessed since the last warm reset, through either secure or plain access. This ensures that boot code receives a valid CDI only when its integrity has not been compromised and no other code has been fetched from flash.

🔗DICE-like attestation sample

LMS-OTS based Device Attestation

The W77QxxN provides hardware support for LMS-OTS attestation and contains a factory-provisioned LMS private key. It can use this key to sign attestation challenges from a local or remote host. The host verifies the signature with the corresponding LMS public key, which Winbond provides to the verifying vendor.

Rollback Protection

Rollback protection is enforced during firmware updates. In addition to swapping the active and inactive section halves, the update configures a new version tag. The tag prevents a later update from installing an older firmware version. For details and code, see Firmware Updates Using Symmetric / Asymmetric Cryptography.

Secure Boot

Secure boot ensures that only authenticated code runs during device startup. W77Q supports this through an integrity-protected boot section and a fallback mechanism. For details, see Platform Firmware Resiliency.
