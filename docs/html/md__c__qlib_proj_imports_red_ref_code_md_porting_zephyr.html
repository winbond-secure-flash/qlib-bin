QLIB User-Guide
Zephyr RTOS

Hardware Abstraction:

Uses the Zephyr Device Driver Model. You interact with the SPI driver via the standard Zephyr SPI API (spi_transceive, spi_write, spi_read). You get a device pointer using device_get_binding().

Implementation:

  • Mutual Exclusion: Handled internally by the Zephyr SPI driver API when you call functions like spi_transceive. It uses spi_context structures to manage locking.
  • Transaction: The spi_transceive() function is ideal here. It takes an array of spi_buf_set structures, where each spi_buf_set contains an array of spi_buf structures (buffers for TX or RX). This allows you to define the entire sequence (write cmd, write addr, write data, dummy clocks (often by TXing null bytes), read data) as a series of buffers within a single API call, ensuring atomicity (CS stays asserted).
  • You would construct spi_buf entries for dataOutStream (potentially splitting cmd, addr, data if required by the underlying driver or for clarity, though often combined into one TX buffer), dummy bytes (a TX buffer with dummy data), and dataIn (an RX buffer).
  • You'd group these into one or more spi_buf_sets.
  • Create an spi_config struct populated based on format, flags, and potentially device-specific settings (speed, operation bits like SPI_OP_MODE_MASTER, SPI_WORD_SET(8), SPI_TRANSFER_MSB, specific mode flags). The userData would likely contain the const struct device *spi_dev pointer and possibly parts of the spi_config.
  • Call spi_transceive(spi_dev, &spi_cfg, &tx_bufs, &rx_bufs). (Modern API uses spi_transceive_dt). The exact structure setup depends slightly on whether the API expects separate TX/RX buffer sets or combined ones. Often, for a write-then-read:
    • TX buffer set: Contains buffers for cmd, addr, data, dummies.
    • RX buffer set: Contains buffer for dataIn.
  • The userData would likely point to a struct containing the Zephyr const struct device * for the SPI controller and perhaps the CS pin configuration if manually controlled (though usually handled by the driver).

Concurrency:

Handled by Zephyr's driver model and kernel locking mechanisms.

Blocking:

spi_transceive is a blocking call from the application's perspective, though the driver underneath likely uses interrupts or DMA efficiently. Asynchronous APIs exist but aren't needed for this synchronous function signature.

Atomicity:

Naturally handled by spi_transceive when defining the whole sequence in one call.

Error Handling:

Zephyr API functions return 0 on success or negative errno codes on failure. Translate these to your library's error codes.
