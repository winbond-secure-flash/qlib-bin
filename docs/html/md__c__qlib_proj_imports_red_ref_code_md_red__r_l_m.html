[RLM] Resilience mechanism

W77Q provides the fundamental contribution to the device RLM with its several features.

Read-only boot memory ( cryptographically write protected boot section )

User can configure boot section to be writable only by authorized user. Other actors can only read from such section. See how to configure such section in SSM example .

Integrity protected fallback ( remapping boot section upon attack )

If during boot data integrity of the boot section is found to be damaged W77Q will automatically boot section ( aka 0 ) to another one in the flash. So in case of attack on boot section device will boot from another one to the firmware which probably handles attack incident, thus staying resilient.

C code implementation

RLM code is split in two phases - manufacture and field. During manufacture we make 3 sections and exercise fallback feature. To achieve this we will spoil boot section integrity and see how in this case read from boot section is mapped to fallback section.

section 0 - [ 0 -> 1MB ]

Boot section to be integrity protected ( in picture). Plain read access is enabled, plain write is disabled. Note that we use checksum (crc32) integrity policy, digest (sha256) is also possible.

section 1 - [ 0 -> 2MB ]

This section will overlap section 0 and used as a "hacker window" to spoil integrity of section 0. Both plain read and write access are enabled.

section 7 - [ 2MB -> 3MB ]

This section is to be fallback section to which section 0 access to be mapped if section 0 integrity is corrupt(in picture). This is where you might store your emergency firmware. Both plain read and write access are enabled.

Integrity monitoring ( periodic digest calculation on the section data )

Another way to keep device resilient is to monitor its integrity. At any moment W77Q can calculate digest (hash function) of flash section so data damage can be detected. Such request can be signed, giving host ( remote or local ) not only the digest value to compare to the expected one but also certainty that this data was provided by W77Q and not spoofed during "man in the middle" attack. In addition, successfully verified signed command can be a basis to the device attestation.
