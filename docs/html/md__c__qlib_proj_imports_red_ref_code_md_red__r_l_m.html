[RLM] Resilience mechanism

W77Q provides fundamental support for the device's resilience mechanism (RLM) through several features.

Read-only boot memory (cryptographically write-protected boot section)

A user can configure the boot section so that only authorized users can write to it. Other actors can read it only. See the SSM example for configuration details.

Integrity-protected fallback (remapping the boot section after an integrity failure)

If the boot section fails its integrity check, W77Q automatically redirects access from the boot section (section 0) to another flash section. If an attack affects the boot section, the fallback section can contain firmware intended to handle the incident, helping maintain resilience.

Example Implementation

The RLM example has two phases: manufacturing and field use. During manufacturing, three sections are configured for the fallback demonstration. During field use, the boot-section integrity is deliberately invalidated to demonstrate how reads are redirected to the fallback section.

Section 0 — [0–1 MB]

This is the boot section protected by an integrity policy. Plain read access is enabled, and plain write access is disabled. This example uses CRC-32; digest-based integrity (SHA-256) is also supported.

Section 1 — [0–2 MB]

This section overlaps section 0 and is used to demonstrate how its integrity can be invalidated. Plain read and write access are enabled.

Section 7 — [2–3 MB]

This is the fallback section to which section 0 access is mapped if section 0 fails its integrity check. It can hold recovery firmware. Plain read and write access are enabled.

Integrity Monitoring (Periodic Digest Calculation for Section Data)

Another way to improve device resilience is to monitor data integrity. W77Q can calculate a digest of a flash section to detect data corruption. The request can be signed, giving the local or remote host both a digest to compare with an expected value and assurance that the response came from W77Q rather than being spoofed in a man-in-the-middle attack. A successfully verified signed command can also support device attestation.
